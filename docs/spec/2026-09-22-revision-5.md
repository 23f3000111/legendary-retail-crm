## One server, every device

Until now this was a single-browser build: each phone and laptop held its
own copy of everything. That is why a promoter's closing never reached Kelly,
and it is the thing that had to change before staff could test it.

Now there is one server — a Supabase project — and every device reads from
and writes to it:

- **Every sale, closing, order, target, promotion and log line** is a document
  on the server. Two promoters ringing up sales on two phones write two
  different documents, so neither overwrites the other.
- **Each device keeps a copy of what it may see** and shows it at once. When
  something is written, the device tells the others; each then asks the server
  for what changed. They also ask on a timer, and whenever the app comes back
  to the front. If the connection drops, the screen says so in the footer and
  keeps showing what it last received.
- **A promoter is sent only their own store.** Head office is sent everything.
  The activity log goes only to the people who may read it.
- **Passwords never reach the browser.** They are checked on the server and
  read back — by the seniors the client allows — only through the look-up that
  is written to the log.
- **The server checks the same rules the app checks:** who may write what,
  who may set and see whose password, that a promoter writes only for the store
  they are at, and that the log is append-only.
- **A line in the log is filed against whoever holds the session**, whatever
  the browser sends. The app writes what happened, in words; who did it is the
  server's to stamp, so no action can be recorded in somebody else's name.

The single-browser build still exists, for the tests and for working on the
code. It is the same rules behind the same interface — `src/api/local.ts` and
`supabase/migrations/0001_init.sql` are twins, and the tests run against the
former.

### What this changes for the security notes

- The key that ships in the app can do nothing on its own: every table is
  closed to it, and every function it may call wants a valid session token.
- A session token is 48 random characters, kept on the device, and lasts a
  month unused.
- Five wrong passwords hold the username for a minute, counted on the server.
- Passwords are stored as bcrypt hashes for checking, and separately
  encrypted with a key held in Supabase Vault for the look-up the client asked
  for. Every password ever held is kept hashed so none is reissued.
- **No password lives in this repository.** The server gives everyone a random
  password when it is set up; Imran signs in with the one password chosen at
  set-up, and reads the rest off the Logins screen to hand out.

### Not yet: the e-mailed code

The second step for leadership needs somewhere to send mail from. The server
is built for it — the setting is `two_step` and the code is generated, hashed
and checked — but it is **off** until a mail sender is connected, so
leadership sign in on the password alone during the trial. See
[`auth.md`](./auth.md).
